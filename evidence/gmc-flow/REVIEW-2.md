## 2. 判讀

### 2.1 PersonPath22 沒有強相機運動的序列

以 PLAN-2 §2.2 的同一指標 m（未遮罩 cells 的 |flow| 中位數，換算到 1080p 寬度）比較：

| 資料 | m（px／幀） |
| --- | --- |
| PP-moving 9 個序列 | 0.51–1.07 |
| MOT17-10／11／13 | 4.90／4.69／5.96 |
| MOT17-05 | 15.09 |
| MOT17-02／04／09 | 0.03／0.06／0.03 |

PP-moving 的相機運動比 MOT17 的移動序列弱 5–15 倍。局部臂設計要解決的是強自我運動下的視差，這種情況在 PersonPath22 裡不存在。所以本輪量到的主要是局部臂的**代價**（固定與輕微運動場景的噪聲注入），沒有量到它在強視差下的**收益**。局部臂的收益至今只出現在設計時用過的 MOT17 移動序列上。

另一個量測限制：RC 與 R 的 control 差距中位數只有 0.07 px，PP-moving HOTA 卻差 0.36。9 個序列的合併指標對微小差異很敏感，±0.4 左右的差距應視為雜訊範圍。

### 2.2 R 的設計缺陷（計畫本身，非實作錯誤）

PP-static 上各臂 control 的大小：

| 臂 | 平均 | p99 | 最大 |
| --- | ---: | ---: | ---: |
| G1 | 0.09 | 1.03 | 51.7 |
| R | 0.51 | 9.68 | 445 |
| L2 | 0.77 | 22.2 | 173 |

最大值的例子：`uid_vid_00048` 第 557 幀。腳點列的三列帶狀區只剩 18 個未遮罩 cells，全部擠在 x 1876–1916（擁擠場景中其餘被偵測框遮住）。直線往 800 px 外的 track 位置外插，得到約 412 px。PLAN-2 §3.1 只要求至少 16 個 cells，沒有要求 x 的涵蓋範圍，也沒有限制外插。這是我在計畫裡的疏漏。

依登記規則，本輪不據此修改，也不重新計分。PersonPath22 已經看過結果，不能再用來驗證任何修正版。

## 3. 建議

- **G1 進入整合規格**：以 OFA＋遮罩中位數取代 F05／F06 的 PCR。輸出仍是單一 (tx, ty)，F08a 與 CUDA tracker 不變。整合規格需涵蓋：
  - OFA 的 stream 順序審查（比照 Bug 7038860）；
  - perf level 的選擇（MEDIUM 的品質尚未測）；
  - 4K 輸入的處理；
  - 完整 MOT 回歸。
- **局部 GMC 暫時結案**（NO-GO，有條件）。復活需要三個條件同時成立：
  1. 有強自我運動、且未用過的評估資料（行走或行車相機），本機目前沒有；
  2. 地面模型加上 x 涵蓋與外插限制；
  3. 只在全域運動強時才啟用局部 control（依 §2.1，這正是收益與代價分界的地方）。

  第 3 點是看過本輪結果後才提出的假設，必須在新資料上預先登記後再驗證。
- **範圍外發現**：`detect_sequence`（DetectionSession）的 JPEG 容量不接受 3840×2160。這與 GMC 無關，另行處理。
